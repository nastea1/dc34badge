# Ko

The secret every DC34 badge shares. Read [01-flag1.md](01-flag1.md) first:
everything here runs inside that payload, and this page assumes all of it. A
styled version with the complete source inline is at [ko.html](ko.html).

## What Ko is

The badge game is collecting light patterns from other people. When two badges
breed, they trade a pattern over QR codes. That trade is encrypted with a key
split in two: **Kp**, published openly and lengthened over the conference so
brute force gets easier each day, and **Ko**, identical on every badge and wiped
the instant a badge enters developer mode.

`defcon-scheme.md:114` says it plainly: *"Extraction of Ko requires a break of the
badge security. Effectively, Ko is a 'flag' that is there to be captured."*

## Where it lives

Not in the keystore. Ko sits in the badge's filesystem, the **PDDB**, on a
**separate SPI flash chip**. The processor cannot read that chip like memory; it
requests blocks over a four-wire bus. And the filesystem is encrypted, three
layers deep:

| Layer | What | Where it comes from |
|---|---|---|
| master key | 32 bytes | HKDF-SHA256 over the root seed and roughly 250 decoy keys, all `Fw0` slots, so all needing the U-mode read from document 1 |
| basis key | 32 bytes | Sitting on the flash chip, wrapped under the master key |
| Ko | 32 bytes | Inside one encrypted 4096-byte page somewhere in a 4 MB region |

### Deriving the master key

`services/keystore/src/platform/baosec/store.rs`:

```
salt = UUID(slot 1) || CP_ID(slot 3)                          :212, :217
ikm  = ROOT_SEED(slot 256)                                    :116
     || nuisance slots 8..128, then 1920..2048, in order       :189
     || chaff_xor = XOR of slots 128..256                      :206
     = (1 + 120 + 128 + 1) * 32 = 8000 bytes  (asserted at     :207)
info = "sec"    (plus "oem", plus "tampered", per the one-way counters)
KEK  = HKDF-SHA256(salt, ikm).expand(info)                     :243
```

The chaff shuffling at `:142-205` is side-channel hardening only. Every chaff slot
is folded into `chaff_xor` either in the loop or the drain, and XOR is
commutative, so an attacker can just read them in order.

`payload/src/bin/ko.rs` does all of this on your badge at runtime. **No key is
hardcoded in this repo.**

### The wrapped basis key

`StaticCryptoData` is **not encrypted**. It is a plain 4096-byte page at a fixed
offset:

```
flash 0x40_3000        (baosec-lite build; the 4 MiB build uses 0x40_4000)
  +0x00  version        u32       must read 2. this is your "found it" check.
  +0x04  system_key_pt  [u8; 40]  wrapped
  +0x2C  system_key     [u8; 40]  wrapped. this is the one I want.
  +0x54  salt_base      [u8; 4012]
```

Those unwrap with RFC 5649 AES key wrap using the master key **directly**.
`store.rs:273` is literally `Kek::from(self.master_key)`. The `"PDDB's key"`
domain separator rides in the message and never reaches `aes_kwp`, so do not
derive anything from it first.

**AES key wrap has a 64-bit integrity check.** If the unwrap succeeds, your key
was right. That is the first genuine oracle in this whole project. My master key
had been unverified for its entire life, because I had been checking against the
UUID slot, which is `PartitionAccess::Open` and readable by everyone. It passed.

## The bug that blocked me for a day

Every flash read returned `0xff` for every byte, which looks exactly like an
empty chip.

The SPI bus runs either one wire (slow, the default) or four (quad, "QPI"). The
chip must be told to switch. `Spim::mem_read()` only ever issues the four-wire
read opcode `0xEB` (`spim.rs:1262`), framed with whatever mode the driver thinks
it is in, and `identify_flash_reset_qpi()` always leaves that at `Standard`
because it ends in `flash_ensure_qe()` which forces it back at `:1446`.

I was shouting a four-lane question down one wire. The chip never replied and
the bus floated to its pulled-up resting state.

```rust
let id_spi = fl.mem_read_id_flash();           // 1-lane RDID; also latches command_set
let sr     = fl.flash_read_status_register();  // 1-lane RDSR
fl.mem_qpi_mode(true);                         // THE MISSING LINE
let id_qpi = fl.mem_read_id_flash();           // confirm in QPI
```

The loader does this at `swap.rs:116`. Boot1 does it at `usb/glue.rs:66`. My
payload was the only code on the chip that did not.

> [!WARNING]
> **Do not call `identify_flash_reset_qpi()`,** convenient as it looks. It ends in
> `flash_ensure_qe()`, whose wait-for-ready loop is
> `loop { if flash_rdsr() & 1 == 0 { break } }` (`spim.rs:1228-1235`). On a bus
> reading `0xff`, `0xff & 1` is 1, so it never exits: black screen, lost boot
> cycle, nothing learned. It can also issue a **permanent** write to the flash
> configuration register. The vendor's own comment at `swap.rs:109` reads *"TODO:
> figure out why writing this causes reads to break (every other read works)"*,
> and they commented out their own call to it.

Reading the ID in both modes separates every failure:

| 1-lane | 4-lane | Meaning |
|---|---|---|
| valid | valid | Transport works |
| valid | `0xffffff` | Chip present, quad-enable bit not set |
| `0xffffff` | `0xffffff` | Unpowered, held in reset, or not wired where you think |

## The shortcut

Having the basis key is not having Ko. Normally you would now parse the
filesystem: page table, decrypt entries, verify checksums, walk to the `dc34`
directory, find `k0`, follow it to a page. Hundreds of lines, every step a chance
to get a byte order wrong and see nothing.

Skip all of it. **The badge's own source contains `sha256(k0)` truncated to four
bytes**, as a self-check, at `dc34-vault/src/main.rs:42`: `dca9ea49`.

So you do not need to know where Ko is. Decrypt every page in the region, hash
every 32-byte window, stop when a hash starts with `dca9ea49`. Roughly two
million hashes, well under a minute on-chip. And unlike every other measurement
in this project, a hit cannot be a false positive.

Every page has the same shape (`hw.rs:60`, `hw.rs:1923`):

```
[ nonce (12) | ciphertext (4068) | tag (16) ]   = 4096 bytes
```

The encryption is AES-GCM-SIV, which normally both hides the data and proves it
was not tampered with. I only want the first job, and skipping the second buys a
lot:

- The tag **is** the CTR seed (RFC 8452 section 4), so decryption needs only the
  key, the nonce and the tag.
- Verification would need the associated data, built from the basis name, a
  version number and the badge DNA in a particular byte order. Three chances to
  be subtly wrong, all avoided.
- The `dca9ea49` oracle is a far stronger check than the tag anyway.

## Procedure

```sh
cd payload
cargo build --release --bin ko
python3 ../tools/elf2bin.py target/riscv32imac-unknown-none-elf/release/ko ko.bin
```

The crypto roughly quintuples the payload, to about 25 KB against the 36 KB
window. `elf2bin.py` prints the headroom.

Cold boot to update mode, confirm `Baochip_1x`, then:

```sh
python3 ../tools/uf2send.py file 0x60090000 ko.bin
python3 ../tools/uf2send.py word 0x60060000 0003006F
```

Power cycle with no button. **Wait about 60 seconds before expecting anything.**
The chip is grinding software AES and SHA-256 across 4 MB with the screen dark.
That is work, not a crash. I nearly power cycled through my own successful run.

Seven pages:

| Page | Contents |
|---|---|
| 1 | flash id 1-lane (3), status register, flash id 4-lane (3), flags |
| 2 | Your UUID control. Wrong means discard the set. |
| 3 | found, `0x5A` marker, where it was found, CRC ends |
| 4 to 7 | **Ko** |

Flags on page 1: bit 0 means `StaticCryptoData` was at `0x40_3000`, bit 1 means
`0x40_4000`, and **bit 6 means the AES key unwrap integrity check passed**, which
also confirms your master key.

```sh
python3 tools/decode.py page*.jpg
python3 tools/verify_ko.py <p4> <p5> <p6> <p7> --diag <page1hex>
```

The `0x5A` on page 3 is a fixed marker. If it decodes as anything else your photo
is misaligned and nothing on that page is trustworthy.

Then restore, exactly as before:

```sh
python3 tools/uf2send.py word 0x60060000 3000006F
```

Nothing was ever written to the flash chip, so the filesystem, saved data and any
custom splash are untouched.

## What I would tell myself at the start

Four things, all the same thing wearing different hats.

1. **An absence is not a measurement.** Reading `0xff` and concluding "the chip is
   blank" was wrong, caught only by adding a read whose answer I already knew.
   Reading zeros from the keystore and concluding "the protection held" was wrong
   the same way.
2. **A control must be in the same class as the claim.** The UUID slot is readable
   by everyone. Passing it said nothing about protected slots. That mistake got
   written into two documents before the AES unwrap settled it.
3. **Look for an oracle before building machinery.** `dca9ea49` was in the vendor's
   source the whole time. Finding it first turned a filesystem parser into a loop,
   and turned "this looks right" into proof.
4. **Diff your code against the vendor's working code.** The missing
   `mem_qpi_mode(true)` cost a day. Two places in the vendor tree call it
   immediately before their first read. I had read both files and never compared
   the sequence.

Pitfalls in detail: [03-troubleshooting.md](03-troubleshooting.md).
