Ko: pulling the shared badge secret out of the encrypted filesystem

Ko is the secret every DC34 badge shares, the one that makes the light-pattern exchange work. It lives on a separate flash chip inside an encrypted filesystem. This explains what that means, how the keys nest inside each other, the one-line bug that blocked us for a day, and the shortcut that made the whole thing a single boot cycle.

Read document 1 first

Everything here runs inside the payload from THE_FLAG_1: how we got it, explained from scratch. That document covers the badge, the boot chain, the unsigned-header flaw, how to get into update mode safely, and how to photograph and decode the screen. This one assumes all of it.

Part 1 · What Ko actually is

The badge game is about collecting light patterns from other people. When two badges "breed", they trade a pattern over QR codes on their screens. That trade is encrypted, and the key is split in two:

  • Kp, the public part. Published openly, and deliberately made longer over the course of the conference so brute-forcing gets easier each day.
  • Ko, the secret part. The same on every badge, and wiped the moment a badge enters developer mode.

The design document says it plainly at defcon-scheme.md:114: "Extraction of Ko requires a break of the badge security. Effectively, Ko is a 'flag' that is there to be captured." You can brute-force it, or you can break the badge. This is the second route.

Worth knowing before you spend a week on it

There is no third flag. THE_FLAG_1 is the only flag slot that exists in the firmware (offsets/baosec.rs:131), and the design document calls Ko the other one. We spent real time hunting a hidden third secret in RRAM, in the chip's factory-programmed region, and in the shipped bitmap images. It was never there.

Part 2 · Where it lives, and the nest of keys around it

Ko is not in the keystore safe from document 1. It sits in the badge's filesystem, which is stored on a separate flash memory chip wired to the processor over a four-wire bus called SPI. The processor cannot simply read that chip like normal memory. It has to ask for each block over the bus, one request at a time.

The filesystem is called the PDDB, and it is encrypted. Getting a value out of it means unwrapping three layers:

LayerWhat it isWhere it comes from
1. master key A 32-byte key derived inside the chip Built by hashing together the root seed and roughly 250 decoy keys from the keystore. Reading those needs document 1's technique.
2. basis key The key that actually decrypts filesystem pages Stored on the flash chip, wrapped (encrypted) under the master key, in a plain-to-find 4096-byte page.
3. the data Ko itself, 32 bytes Inside one encrypted 4096-byte page somewhere in a 4 MB region.

Layer 2 is the interesting one. The page holding the wrapped keys is called StaticCryptoData, and it is not encrypted. It is just sitting there at a fixed offset, with a known layout:

flash offset 0x40_3000        // baosec-lite build (0x40_4000 on the 4 MiB build)
  +0x00  version        u32       // must read 2. this is your "found it" check.
  +0x04  system_key_pt  [u8; 40]  // wrapped
  +0x2C  system_key     [u8; 40]  // wrapped. this is the one we want.
  +0x54  salt_base      [u8; 4012]

Those 40-byte blobs are unwrapped with a standard called AES key wrap, using the master key directly. No further derivation, no salt, no hashing: store.rs:273 is literally Kek::from(self.master_key).

The part that makes this trustworthy

AES key wrap has a built-in 64-bit integrity check. If the unwrap succeeds, the key you used was correct, with overwhelming probability.

That matters a lot here. Our master key had been unverified for the entire project. We had been checking our work against the badge's serial-number slot, and that slot is readable by everyone, so a successful read never proved we could reach the protected ones. This unwrap is the first genuine proof. It passed.

Part 3 · The bug that cost us a day

Every attempt to read the flash chip returned 0xff for every byte. That looks exactly like an empty chip, and we nearly wrote it off as one.

Here is what was actually happening. The SPI bus can run in two speeds: one wire (slow, the default) or four wires (fast, called quad or QPI mode). The chip has to be told to switch. The read function in the badge's own driver, Spim::mem_read(), only ever issues the four-wire read command 0xEB (spim.rs:1262), and it frames that command using whatever mode the driver currently thinks it is in.

Our payload never switched the chip into quad mode. So we were shouting a four-lane question down a single wire. The chip did not recognise the command, never replied, and the bus floated to its resting state, which the board pulls high. All ones. Forever.

let id_spi = fl.mem_read_id_flash();          // 1-lane. also latches command_set.
let sr     = fl.flash_read_status_register(); // 1-lane.
fl.mem_qpi_mode(true);                        // <-- THIS. one line.
let id_qpi = fl.mem_read_id_flash();          // now confirm it in 4-lane mode.

The loader does this at swap.rs:116. Boot1 does it at usb/glue.rs:66. Our payload was the only code on the chip that did not.

Do not call identify_flash_reset_qpi(), even though it looks right

There is a convenient-looking setup function that seems to do all of this for you. Avoid it. It ends by calling flash_ensure_qe(), whose wait-for-ready loop is loop { if rdsr & 1 == 0 { break } } (spim.rs:1228-1235). On a bus that reads 0xff, 0xff & 1 is 1, so it never exits. You get a black screen and lose a boot cycle, with nothing to show for it.

Worse, it can issue a permanent write to the flash chip's configuration register. The loader's own source comment at swap.rs:109 reads: "TODO: figure out why writing this causes reads to break (every other read works)." The vendor commented out their own call to it. Take the hint.

A useful diagnostic falls out of this. Reading the chip's ID in both modes separates every possible failure:

Part 4 · The shortcut

Having the basis key is not the same as having Ko. Normally you would now parse the filesystem: read its page table, decrypt each entry, verify a checksum, walk to the directory named dc34, find the entry named k0, follow it to the right page. That is a few hundred lines of fiddly code, and every one of those steps is a chance to get a byte order wrong and see nothing.

We skipped all of it.

The idea

The badge's own source code contains sha256(k0) truncated to four bytes, as a self-check. It is right there at dc34-vault/src/main.rs:42: dca9ea49.

So we do not need to know where Ko is. Decrypt every page in the region, hash every 32-byte window inside each one, and stop when a hash starts with dca9ea49. That is roughly 2 million hashes, which the chip chews through in well under a minute. And unlike every other measurement in this project, a hit cannot be a false positive.

Every page has the same shape (hw.rs:60, hw.rs:1923):

[ nonce (12 bytes) | ciphertext (4068 bytes) | tag (16 bytes) ]   = 4096 bytes

The encryption is AES-GCM-SIV. It normally does two jobs: it hides the data, and it proves the data was not tampered with. We only want the first job, and skipping the second one buys a lot:

  • In GCM-SIV, the tag is the counter seed for decryption (RFC 8452 section 4). So decryption needs nothing but the key, the nonce, and the tag.
  • Verification would need the associated data, which is built from the filesystem's name for the partition, a version number, and the badge's DNA value in a particular byte order. Three chances to be subtly wrong, all of them avoided.
  • We do not need integrity checking anyway. The dca9ea49 oracle is a far stronger check than the tag would have been.

  1. Start from the document 1 payload

    The crypto code roughly doubles the payload, from about 12 KB to about 24 KB. The window between the loader and the operating system is only 36 KB. Ours landed at 0x60095E84, leaving 12668 bytes of headroom. elf2bin.py from document 1 asserts this, so let it.

  4. Power cycle, then wait

    Wait about 60 seconds before you expect anything. The chip is grinding software AES and SHA-256 across 4 MB, and the screen stays dark the whole time. That is work, not a crash. We nearly power-cycled through our own successful run.

  5. Photograph seven pages and decode

    Same decoder as document 1. The pages are:

    PageContents

src/ko.rsAES key unwrap + GCM-SIV + the oracle
//! Ko extraction crypto: AES-KWP unwrap, AES-GCM-SIV decrypt-without-verify.
//!
//! Verification is deliberately skipped: POLYVAL is unnecessary because in GCM-SIV
//! the stored tag *is* the CTR seed (RFC 8452 §4), and we have a far better oracle
//! than the tag: `sha256(k0)[..4] == dca9ea49`, published in the vendor's own
//! source at dc34-vault/src/main.rs:42. Skipping the tag also retires every
//! AAD-byte-order risk (basis name, PDDB_VERSION, DNA endianness).

use aes::Aes256;
use aes::cipher::generic_array::GenericArray;
use aes::cipher::{BlockDecrypt, BlockEncrypt, KeyInit};

/// RFC 5649 AES-KWP unwrap of a 40-byte blob to 32 bytes.
///
/// The AIV check is 64 bits wide, so a pass is strong evidence the KEK is right.
/// That makes this the master key's first real correctness oracle. The UUID slot
/// never was one, because `PartitionAccess::Open` is readable by every coreuser id.
pub fn kwp_unwrap(kek: &[u8; 32], ct: &[u8; 40], out: &mut [u8; 32]) -> bool {
    let c = Aes256::new(GenericArray::from_slice(kek));
    const N: usize = 4; // 40/8 - 1
    let mut a = [0u8; 8];
    a.copy_from_slice(&ct[0..8]);
    let mut r = [[0u8; 8]; N];
    for i in 0..N {
        r[i].copy_from_slice(&ct[8 + 8 * i..16 + 8 * i]);
    }
    for j in (0..6usize).rev() {
        for i in (1..=N).rev() {
            let t = (N * j + i) as u64;
            let mut blk = [0u8; 16];
            blk[0..8].copy_from_slice(&(u64::from_be_bytes(a) ^ t).to_be_bytes());
            blk[8..16].copy_from_slice(&r[i - 1]);
            let mut g = *GenericArray::from_slice(&blk);
            c.decrypt_block(&mut g);
            a.copy_from_slice(&g[0..8]);
            r[i - 1].copy_from_slice(&g[8..16]);
        }
    }
    for i in 0..N {
        out[8 * i..8 * i + 8].copy_from_slice(&r[i]);
    }
    // KWP AIV = A65959A6 || MLI(be32); MLI must be 32 for a 256-bit key.
    a[0] == 0xA6
        && a[1] == 0x59
        && a[2] == 0x59
        && a[3] == 0xA6
        && u32::from_be_bytes([a[4], a[5], a[6], a[7]]) == 32
}

/// AES-GCM-SIV CTR pass, in place. RFC 8452 §4: derive per-nonce keys, then CTR
/// seeded with the tag, MSB of the last byte forced to 1, counter = LE u32 at [0..4].
pub fn gcm_siv_ctr(key: &[u8; 32], nonce: &[u8; 12], tag: &[u8; 16], data: &mut [u8]) {
    let c = Aes256::new(GenericArray::from_slice(key));
    let mut enc = [0u8; 32];
    for i in 0..6u32 {
        let mut b = [0u8; 16];
        b[0..4].copy_from_slice(&i.to_le_bytes());
        b[4..16].copy_from_slice(nonce);
        let mut g = *GenericArray::from_slice(&b);
        c.encrypt_block(&mut g);
        // blocks 0..1 make the auth key (unused here); 2..5 make the 256-bit enc key
        if i >= 2 {
            let o = (i as usize - 2) * 8;
            enc[o..o + 8].copy_from_slice(&g[0..8]);
        }
    }
    let ec = Aes256::new(GenericArray::from_slice(&enc));
    let mut ctr = *tag;
    ctr[15] |= 0x80;
    let mut off = 0usize;
    while off < data.len() {
        let mut g = *GenericArray::from_slice(&ctr);
        ec.encrypt_block(&mut g);
        let n = core::cmp::min(16, data.len() - off);
        for k in 0..n {
            data[off + k] ^= g[k];
        }
        let v = u32::from_le_bytes([ctr[0], ctr[1], ctr[2], ctr[3]]).wrapping_add(1);
        ctr[0..4].copy_from_slice(&v.to_le_bytes());
        off += 16;
    }
}

/// The published oracle. Returns the offset of the first 32-byte window whose
/// SHA-256 begins dc a9 ea 49, or None.
pub fn find_k0(buf: &[u8]) -> Option<usize> {
    use sha2::{Digest, Sha256};
    if buf.len() < 32 {
        return None;
    }
    let mut w = 0usize;
    while w + 32 <= buf.len() {
        let d = Sha256::digest(&buf[w..w + 32]);
        if d[0] == 0xdc && d[1] == 0xa9 && d[2] == 0xea && d[3] == 0x49 {
            return Some(w);
        }
        w += 4;
    }
    None
}

// src/main.rs, the Ko half. The U-mode section is unchanged from document 1;
// only the machine-mode `render()` differs, so that is what is shown here.
// The full file is document 1's payload with this function swapped in, plus

mod ko;

/// Derived on-chip in an earlier run (see document 1's technique applied to the
/// keystore's HKDF inputs). The AES-KWP AIV check below is its FIRST real
/// correctness oracle: the UUID slot never was one, because it is
/// PartitionAccess::Open and every coreuser id can read it.
const MASTER_KEY: [u8; 32] = [
    0xb9,0x4b,0xc9,0x7f,0x73,0x28,0x2b,0xd5,0xfe,0x0a,0x30,0xf6,0xac,0xec,0x58,0x4e,
    0x56,0xb5,0x7e,0x23,0xc3,0x23,0xc1,0xb6,0x32,0xe2,0x37,0x8e,0x59,0x08,0x81,0x80,
];

#[unsafe(no_mangle)]
pub extern "C" fn render() -> ! {
    unsafe { core::arch::asm!("csrw satp, zero", "sfence.vma"); }
    let iox  = bao1x_hal::iox::Iox::new(utralib::utra::iox::HW_IOX_BASE as *mut u32);
    let udma = bao1x_hal::udma::GlobalConfig::new();
    let mut oled = open_oled(&iox, &udma);
    let u = unsafe { *core::ptr::addr_of!(RES_U) };   // UUID control from the U-mode phase

    // ---- SPI FLASH bring-up ------------------------------------------------
    // Deliberately NOT identify_flash_reset_qpi(). It ends in flash_ensure_qe()
    // (spim.rs:1029 -> :1446), whose write-in-progress wait is
    //     loop { if rdsr & 1 == 0 { break } }        (spim.rs:1228-1235)
    // On a bus reading 0xFF, 0xFF & 1 == 1 forever: a dark screen and a lost
    // boot cycle. It can also issue a NON-VOLATILE status-register write, and
    // the loader's own comment at swap.rs:109 says that write breaks later
    // reads. Everything below is read-only against the flash device.
    use bao1x_hal::{board::setup_memory_pins, ifram::IframRange, udma::*};
    use bao1x_api::udma::PeriphId;
    const PERCLK: u32 = 100_000_000;

    let channel = setup_memory_pins(&iox);
    udma.clock_on(PeriphId::from(channel));
    let mut fl = unsafe {
        Spim::new_with_ifram(
            channel,
            PERCLK / 2,                     // spi_clk
            PERCLK,                         // sys_clk -> clk_div = 2, same as the loader
            SpimClkPol::LeadingEdgeRise,
            SpimClkPha::CaptureOnLeading,
            SpimCs::Cs0,                    // Cs0 is FLASH. Cs1 is PSRAM: wrong chip.
            0, 0, None,
            16,                             // tx buffer
            4096,                           // rx buffer, one page
            Some(6),                        // 0xEB needs 6 dummy cycles (spim.rs:1260)
            None,                           // = SpimMode::Standard
            IframRange::from_raw_parts(
                bao1x_hal::board::SPIM_FLASH_IFRAM_ADDR,
                bao1x_hal::board::SPIM_FLASH_IFRAM_ADDR,
                4096 * 2,
            ),
        )
    };
    // 1-lane RDID first. Pure read, needs no QE bit, and it latches command_set,
    // which mem_qpi_mode(true) needs in order to pick opcode 0x35 vs 0x38.
    let id_spi = fl.mem_read_id_flash();
    let sr     = fl.flash_read_status_register();
    fl.mem_qpi_mode(true);          // <-- THE ONE MISSING LINE. loader swap.rs:116.
    let id_qpi = fl.mem_read_id_flash();

    // ---- find the key page and unwrap the basis key ------------------------
    // baosec-lite puts StaticCryptoData at flash 0x40_3000; the 4 MiB build puts
    // it at 0x40_4000. Read both rather than betting on the build config.
    let mut page       = [0u8; 4096];
    let mut sysk       = [0u8; 32];
    let mut scd_flags  = 0u8;
    for (bit, scd_at) in [(0u8, 0x0040_3000u32), (1u8, 0x0040_4000u32)] {
        fl.mem_read(scd_at, &mut page[..], false);
        if u32::from_le_bytes([page[0], page[1], page[2], page[3]]) == 2 {   // SCD_VERSION
            scd_flags |= 1 << bit;
            let mut wrapped = [0u8; 40];
            wrapped.copy_from_slice(&page[0x2C..0x2C + 40]);   // system_key, hw.rs:79-89
            if ko::kwp_unwrap(&MASTER_KEY, &wrapped, &mut sysk) {
                scd_flags |= 0x40;      // AIV passed: MASTER KEY CONFIRMED CORRECT
                break;
            }
        }
    }

    // ---- exhaustive decrypt-and-oracle sweep -------------------------------
    // No filesystem parsing at all. Every page is
    //     [ nonce(12) | ciphertext(4068) | tag(16) ]        hw.rs:60, :1923
    // so decrypt each one and SHA-256 every 32-byte window against the prefix
    // dca9ea49, which the vendor published in dc34-vault/src/main.rs:42.
    // A hit is proof. There is no way to fool this check.
    let mut k0     = [0u8; 32];
    let mut hit_at = 0xFFFF_FFFFu32;
    let mut off    = 0x0040_0000u32;                 // PDDB_ORIGIN
    while off < 0x0080_0000 {
        fl.mem_read(off, &mut page[..], false);
        // raw pass first: a cheap hedge in case k0 is not stored encrypted
        if let Some(w) = ko::find_k0(&page[..]) {
            k0.copy_from_slice(&page[w..w + 32]);
            hit_at = off + w as u32;
            break;
        }
        if scd_flags & 0x40 != 0 {
            let mut nonce = [0u8; 12];  nonce.copy_from_slice(&page[0..12]);
            let mut tag   = [0u8; 16];  tag.copy_from_slice(&page[4080..4096]);
            ko::gcm_siv_ctr(&sysk, &nonce, &tag, &mut page[12..4080]);
            if let Some(w) = ko::find_k0(&page[12..4080]) {
                k0.copy_from_slice(&page[12 + w..12 + w + 32]);
                hit_at = off | 0x8000_0000;          // high bit: found after decryption
                break;
            }
        }
        off += 4096;
    }

    // ---- report ------------------------------------------------------------
    let kc = crc32(&k0);
    let p1 = [(id_spi >> 16) as u8, (id_spi >> 8) as u8, id_spi as u8, sr as u8,
              (id_qpi >> 16) as u8, (id_qpi >> 8) as u8, id_qpi as u8, scd_flags];
    let p3 = [if hit_at == 0xFFFF_FFFF { 0 } else { 1 }, 0x5A,
              (hit_at >> 24) as u8, (hit_at >> 16) as u8,
              (hit_at >> 8) as u8, hit_at as u8,
              (kc >> 24) as u8, kc as u8];
    loop {
        draw_page8(oled.buffer_mut(), &p1,       1); oled.redraw().ok(); spin(400_000_000);
        draw_page8(oled.buffer_mut(), &u[0..8],  2); oled.redraw().ok(); spin(400_000_000);
        draw_page8(oled.buffer_mut(), &p3,       3); oled.redraw().ok(); spin(400_000_000);
        for p in 0..4usize {
            draw_page8(oled.buffer_mut(), &k0[p*8..p*8+8], p + 4);
            oled.redraw().ok(); spin(400_000_000);
        }
    }
}

"""

SPI_FLASH_IDS = [0x1820c2, 0x3825c2, 0x17600b, 0x1732ba, 0x172085]

args = sys.argv[1:]
diag = None
if "--diag" in args:
    i = args.index("--diag"); diag = args[i+1]; args = args[:i]

    d = bytes.fromhex(diag)

    print("\npage 1 diagnostics")

Part 8 · What we would tell ourselves at the start

Four things, all of them the same thing wearing different hats.

  1. An absence is not a measurement. Reading 0xff from the flash and concluding "the chip is blank" was wrong, and we only caught it by adding a read whose answer we already knew. Reading zeros from the keystore and concluding "the protection held" was wrong the same way.
  2. A control has to be in the same class as the claim. The serial-number slot is readable by everyone. Passing it never said anything about the protected slots. We wrote that mistake into two documents before the AES unwrap finally settled it.
  3. Look for an oracle before you build the machinery. The dca9ea49 check was in the vendor's source the whole time. Finding it first turned several hundred lines of filesystem parsing into a loop, and turned "this looks right" into proof.
